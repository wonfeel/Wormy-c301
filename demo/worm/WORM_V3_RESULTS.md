## 1. Что реально сделано

Механизм раздела 2 `WORM_V3_DESIGN.md` (пространственная изгибная жёсткость
между соседними суставами, дискретный лапласиан, free-free граничные
условия) реализован РОВНО так, как описано в спеке, без отклонений:

1. **`connectome/body.hpp`**: добавлено приватное поле `float
   bend_stiffness_ = 0.0f;` и публичный сеттер `set_bend_stiffness(float k)`,
   с докстрингом, объясняющим и уравнение, и explicit-подтверждение того, что
   `solve_propulsion`/3x3 Крамер не затрагиваются.
2. **`connectome/body.cpp`**, `WormBody::step()`: снимок `anglesPrev =
   angles_` снимается ДО существующего цикла обновления углов (чтобы связь
   была симметричной, не зависящей от порядка обхода `i`). Внутри цикла, ДО
   строки decay/clamp, добавлена строка `angles_[i] += bend_stiffness_ *
   bend * dt;`, где `bend = anglesPrev[i-1] - 2*anglesPrev[i] +
   anglesPrev[i+1]` (зеркальные фиктивные узлы на концах цепи). Больше НИЧЕГО

   явным построчным подтверждением).
3. **`WormSim.h`**: новое поле `Params::bodyBendStiffness{0.0f}` рядом с

4. **`WormSim.cpp`**, `WormSim::step()`: рядом с `m_body.set_pose_decay_rate(

### 4.1 Честная методологическая находка, не входящая в мандат задачи, но обнаруженная в процессе

При попытке построить геометрическую диагностику раздела 5.4 (см. раздел 8
ниже) прямым сравнением `trace`-дампа при одном и том же `seed` между двумя
отдельными запусками процесса обнаружилось, что **траектории НЕ совпадают
побитово** несмотря на идентичный CLI-аргумент `seed`. Причина найдена прямым
чтением кода: `WormSim::WormSim` (`WormSim.cpp`, начало конструктора)
безусловно вызывает `std::srand(static_cast<unsigned>(std::time(nullptr)));`
- это ПЕРЕЗАПИСЫВАЕТ любой `std::srand(seed)`, вызванный харнессом (в т.ч.
`tests/worm_v2_measurement`'s `runTrial`/`trace`-режим) НЕПОСРЕДСТВЕННО ПЕРЕД
конструированием `WormSim`. Практически это означает, что CLI-аргумент
`seed` НЕ управляет шумовой (`signedNoise`) реализацией вообще - реальный
(неконтролируемый) источник шумовой энтропии - момент системного времени
конструирования каждого `WormSim`.

Это НЕ баг, внесённый в этой сессии - код конструктора не тронут ни этой, ни
предыдущей (v2) сессией. Проверено эмпирически: два отдельных запуска
`trace`-режима с идентичным `seed=12345` дают РАСХОДЯЩИЕСЯ траектории углов
(`angles()`) уже с шага 1 (малое начальное расхождение, усиленное дальше
хаотической динамикой сети); отдельно - два запуска, оказавшиеся достаточно
близко по времени выполнения, чтобы попасть в ОДНУ и ту же секунду
(`std::time()`-разрешение), дали ПОБИТОВО идентичный вывод. **Важно**:
агрегатные (по многим прогонам) статистики `point`-режима (health/speed/freq)
эмпирически ОКАЗАЛИСЬ воспроизводимыми между повторными запусками с одним и
тем же CLI (см. раздел 6 ниже - два независимых запуска той же 16-базовой
команды дали идентичные до 4 значащих цифр агрегатные `speed`/`freq`) - то
есть эмерджентная динамика сети (устойчивый предельный цикл) статистически
НЕ чувствительна к КОНКРЕТНОЙ шумовой реализации, только отдельные траектории
чувствительны (типичное поведение слабо-зашумлённого аттрактора) - агрегатные
выводы этого отчёта ДОСТОВЕРНЫ несмотря на эту находку, но
**побитовая одно-прогонная воспроизводимость по заявленному `seed`, на
которую полагается методология `trace`-режима, - нет.** Не исправлено в этой
сессии (вне мандата - было бы отдельным, самостоятельным изменением
`WormSim.cpp`'s конструктора с широким blast radius). Вынесено отдельной
фоновой задачей (см. текстовый чат-лог этой сессии), не в мандате WORM_V3.

механизмом эффект уже откалиброванной оси `bodyPoseDecayRate`. Это **вне
мандата этой задачи** (переоткрытие уже свипанной в v2 оси, а не проверка
НОВОГО механизма) - зафиксировано честно как открытое наблюдение, НЕ
исследовано дальше и НЕ включено ни в какое решение этого отчёта. Решение по

вода). Путевая эффективность (`eff=netDisp/pathLen`, установленная в проекте
метрика "здоровья траектории", НЕ то же самое, что "пропульсивная
эффективность" ниже) тоже чуть выше (агар 0.501->0.516, вода 0.466->0.479,
средние по 16 значений `eff=` из полного вывода). **По всем этим трём
метрикам новый механизм - честный, небольшой позитив.**

## 8. Пропульсивная эффективность (distance/cycle = speed/freq) - РЕШАЮЩАЯ метрика этой задачи

Мандат этой задачи прямо определяет искомую метрику: "propulsion efficiency
(distance per bend cycle equals speed divided by frequency)". Пересчёт всех
чисел разделов 5 и 7 по этой формуле:

| `bodyBendStiffness` | агар distance/cycle (BL) | вода distance/cycle (BL) |
|---|---|---|
| 0 (референс, экран) | 0.03348 | 0.03805 |
| 0.05 | 0.03316 (-0.9%) | 0.03778 (-0.7%) |
| 0.1 | 0.03281 (-2.0%) | 0.03740 (-1.7%) |
| 0.15 | 0.03270 (-2.3%) | 0.03731 (-1.9%) |
| 0.2 | 0.03259 (-2.7%) | 0.03718 (-2.3%) |
| 0.25 | 0.03293 (-1.6%) | 0.03755 (-1.3%) |
| 0.5 | 0.03095 (-7.6%) | 0.03533 (-7.1%) |
| 0.75 | 0.02995 (-10.5%) | 0.03417 (-10.2%) |
| 1.0 | 0.02936 (-12.3%) | 0.03356 (-11.8%) |
| 1.25 | 0.02935 (-12.3%) | 0.03362 (-11.6%) |
| 1.5 | 0.02925 (-12.6%) | 0.03393 (-10.8%) |
| 1.75 | 0.02905 (-13.2%) | 0.03380 (-11.2%) |
| **16-базовое подтверждение, `bendStiffness=1.0`** | **0.02962 (-18.0%)** | **0.03403 (-17.3%)** |

**Вывод, без смягчения**: `distance/cycle` (пропульсивная эффективность)
падает МОНОТОННО, начиная с САМОГО МАЛОГО проверенного ненулевого значения
(`0.05`), в ОБЕИХ средах, на ЛЮБОЙ точке экрана - нет ни одной проверенной
ненулевой точки, где эта метрика была бы лучше референса. На выбранной по
health/скорости "лучшей" точке (`bendStiffness=1.0`, 16-базовое
подтверждение) эффективность на 17-18% ХУЖЕ референса на ОБЕИХ средах.

**Механизм эффекта (прямое измерение, не спекуляция)**: `bodyBendStiffness`
подталкивает частоту вверх (0.3098Гц -> 0.3900Гц на референс/кандидат, +26%)
СИЛЬНЕЕ, чем скорость (+3-4%) - та же категория эффекта, что уже
задокументирована в `WORM_V2_RESULTS.md` разделах 10.2/10.4 для
`muscleCalciumTau`/`bodyPoseDecayRate`: коэффициент связи сидит ВНУТРИ
замкнутого контура проприоцепция -> сеть -> мышца -> изгиб -> проприоцепция
(`applyProprioception` читает `m_body.angles()`, тот самый вектор, который
изгибная жёсткость сглаживает ДО того, как он туда попадёт) - сглаживание
пространственного рельефа кривизны сдвигает частоту САМОВОЗБУЖДЕНИЯ контура
вверх, а не просто фильтрует высокие частоты пассивно. Поскольку RFT-тяга
масштабируется с формой/амплитудой изгиба, а не линейно с числом циклов в
секунду, более частая, но не пропорционально более широкая по амплитуде
волна даёт БОЛЬШЕ циклов за то же время при ПОЧТИ той же суммарной
дистанции за прогон - отсюда рост абсолютной скорости при падении
дистанции-на-цикл. Это - количественно точная, измеренная версия failure
mode, который план честно предсказал ЗАРАНЕЕ (раздел 4 п.3: "слишком большой
`bend_stiffness_`... тело выпрямляется быстрее, чем сеть успевает его
изогнуть") - в реальности это оказалось не катастрофическим коллапсом
амплитуды (health остаётся 4/4 до 1.25), а более тонким, но столь же
решающим эффектом: рост частоты ОПЕРЕЖАЕТ рост амплитуды/скорости на КАЖДОМ
шаге сетки, без исключения.

## 9. Геометрическая диагностика (Rieser et al. 2024) - реализована, результат НЕОДНОЗНАЧНЫЙ из-за находки раздела 4.1

ведущие компоненты, формула шнурков на замкнутой траектории `(w1(t),
w2(t))`) написан и прогнан на 600-шаговых записях (после отброса 300-шагового
транзиента) для агара/воды при `bendStiffness={0, 1.0}`:

| конфигурация | |площадь| (шнурки) | доля дисперсии PC1+2 |
|---|---|---|
| агар, bend=0 | 0.3218 | 92.0% |
| вода, bend=0 | 0.3402 | 93.7% |
| агар, bend=1.0 | 0.1698 | 97.1% |
| вода, bend=1.0 | 0.1698 (побитово = агар) | 97.1% |

На первый взгляд похоже на сигнал, но честно ОТМЕНЯЛОСЬ находкой раздела
4.1 (`srand(time(nullptr))` в конструкторе `WormSim` затирал переданный сид -
агар и вода при `bend=1.0` дали ПОБИТОВО идентичную площадь, что доказывало:
оба запуска случайно попали в одну и ту же шумовую реализацию, не потому что
среды структурно идентичны).

**ОБНОВЛЕНИЕ (после исправления бага, раздел 9 - да, два раздела "9" в этом
файле, второй занят фиксом; смотри дальше по документу): диагностика
пересчитана честно, с настоящими независимыми сидами.** Не на `bendStiffness`
(тот уже дал решающий отрицательный результат в разделе 8, отдельным честным
статистическим измерением), а на исходном мотивирующем случае - агар/вода
при `localMechanoGain=0.2` (`mechanoGain=0`, точка из
`WORM_V2_MECHANOSENSATION_JOINT_RESULTS.md`, где вода здорова по форме/курсу,
но стабильно проваливается по эффективности пути). 20 НЕЗАВИСИМЫХ сидов на
среду (не 1, как в отменённой таблице выше), PCA (92-98% дисперсии в PC1+2 на
каждом прогоне) + площадь по формуле шнурков на замкнутой (w1,w2)-траектории:

| среда | n | среднее | медиана | диапазон |
|---|---|---|---|---|
| агар | 20 | 0.0966 +/- 0.0192 | 0.0769 | 0.0017 - 0.3646 |
| вода | 20 | 0.0404 +/- 0.0052 | 0.0481 | 0.0009 - 0.0714 |

Разница средних: 0.0562 +/- 0.0199 (**2.83 sigma**). Непараметрическая
проверка (агар > вода в скольки из 400 возможных пар): **281/400 (70.2%)**
против 50% при нулевой гипотезе "нет разницы" - согласуется с
параметрической оценкой, не противоречит ей несмотря на сильно скошенное
распределение агара (редкие большие выбросы вроде 0.3646).

**Честный вывод**: реальный, умеренно значимый (2.83 sigma, не
подавляющий) сигнал в направлении, согласующемся с гипотезой теоремы о
весле (раздел research: Perselл 1977 применим к плаванию нематод напрямую) -
вода при этом операционном режиме держит МЕНЬШУЮ площадь в
пространстве главных компонент кривизны, то есть её движение ближе к
реципрокному (не-бегущему), чем у агара - что качественно совпадает с
наблюдаемым провалом по эффективности пути именно в воде. Не окончательное
доказательство (умеренная, не подавляющая статистика; сам метод даёт
разброс на порядок между отдельными сидами в агаре - шумная метрика), но
впервые за сессию - настоящий, статистически осмысленный сигнал по этому
вопросу, а не методологический тупик, как три предыдущие попытки.

## 10. Итоговое решение

Ship-критерий плана (раздел 5.3): включать в дефолт ТОЛЬКО если SURVIVAL
держится на уровне референса И quality-метрика РЕАЛЬНО лучше референса.
SURVIVAL держится (даже чуть лучше - раздел 7). Но **decisive quality-метрика
этой конкретной задачи (distance/cycle, раздел 8) РЕАЛЬНО и монотонно хуже
референса на каждой проверенной точке** - критерий не выполнен.

**`bodyBendStiffness` остаётся `0.0` (выключено) в дефолте `WormSim.h`.**
Механизм реализован, собран, протестирован, документирован и оставлен
доступным (поле `Params`, сеттер `WormBody::set_bend_stiffness`, UI-слайдер,
CLI-аргумент харнесса) для будущего исследования - тот же честный паттерн,
что `dragSettleGain` в его собственный момент предложения, только с
противоположным по знаку итогом на решающей метрике. Структурная находка
(механизм безопасен, 3x3 Крамер не тронут, health не ломается в разумном
диапазоне) - позитивна и полезна сама по себе; эффективностная находка
(distance/cycle монотонно хуже) - отрицательна и является главным честным
результатом этой сессии.

Это - ПОЛНОСТЬЮ ожидаемый и явно допустимый мандатом исход ("ни один
кандидат не оправдывает внедрения" - валидный вывод, `WORM_V3_DESIGN.md`
раздел 6, последний абзац). Не является поводом искать пятый обходной путь
без паузы - главный, самый старый разрыв проекта (абсолютная скорость
10-30x ниже настоящего червя, propulsion efficiency/distance-per-cycle)
остаётся НЕ решённым этой сессией, как и было честно предсказано планом
(раздел 4 п.3: "средняя-низкая уверенность... честно спекулятивная
экстраполяция").

## 11. Честный список нерешённого / открытых вопросов

1. **Пропульсивная эффективность (distance/cycle) остаётся главным,

   `std::srand(time(nullptr))`, перезаписывая любой явный `seed` вызывающего
   кода)** - подтверждённый, но НЕ исправленный в этой сессии баг
   методологии, затрагивающий, вероятно, воспроизводимость ЛЮБОГО
   одно-прогонного (`trace`-подобного) сравнения во ВСЕХ существующих
   `tests/worm_*` харнессах этого проекта, не только новых. Не отменяет
   агрегатные (по многим прогонам) выводы этого и предыдущих отчётов
   (эмпирически показана воспроизводимость АГРЕГАТНЫХ статистик), но делает
   недостоверным буквальное "тот же seed -> тот же прогон" сравнение везде,
   где оно использовалось. Вынесено отдельной фоновой задачей, не в мандате
   этой сессии её чинить.
3. **Честный тангенциальный намёк на `bodyPoseDecayRate=0.55` (раздел 6)** -
   систематически выше скорости, чем шипнутый `0.6`, независимо от
   `bendStiffness`, во всех девяти точках проверенной сетки. НЕ исследовано
   дальше (вне мандата этой задачи - переоткрытие уже свипанной оси) - честно
   зафиксировано как открытое наблюдение для будущей сессии, если она решит
   вернуться к `bodyPoseDecayRate` как таковому.
4. **Геометрическая диагностика (раздел 9)** - инфраструктура готова и
   работает (92-97% объяснённой дисперсии первыми двумя компонентами,
   заметно чище трёх предыдущих попыток из `WORM_V2_RESULTS.md` раздела

   многим независимым прогонам протокола, чтобы дать честный, не спутанный

5. **Совместный (не последовательный) поиск `bodyBendStiffness` x
   `dragSettleGain`** не проводился (план не требовал этого явно, раздел 5.2

## 13. Исправлен найденный баг: `srand(time(nullptr))` в конструкторе WormSim

Найден агентом реализации при работе над геометрической диагностикой фазы
(раздел 6): `WormSim::WormSim` (`WormSim.cpp`, было строка 54) безусловно
вызывал `std::srand(time(nullptr))` - затирая ЛЮБОЙ сид, который вызывающий
код выставлял своим `std::srand(seed)` ДО создания `WormSim`. Каждый
тестовый харнесс в проекте (`tests/worm_*`) делает именно это и полагается
на то, что сид реально подействует.

**Реальное следствие**: весь шум внутри симуляции (`frand()`/
`signedNoise()`, используется в хемотаксисе, термотаксисе, механосенсации,
внутреннем шуме сети - каждый шаг) шёл по последовательности,
инициализированной ВРЕМЕНЕМ КОНСТРУКЦИИ объекта, а не переданным сидом. То
есть аргумент "seed" почти во всех тестах этой сессии не давал контроля над
конкретным прогоном.

**Что это НЕ затронуло**: агрегатную статистику по многим независимым
прогонам (health-fraction, средние по 16+ базам, все health-gated
свипы/подтверждения этой сессии) - реальная случайность там всё равно
бралась (просто из wall-clock времени, а не из указанного числа), и
конструкция "16 независимых баз" оставалась содержательной с точки зрения
статистики.

**Что это ЗАТРОНУЛО**: любое утверждение вида "тот же сид -> тот же
прогон", в частности:
- Сравнение пространственной фазы кривизны agar/water трассировкой на
  одинаковом `seed=999` (раздел про фазовую когерентность, обсуждение до
  workflow с механосенсацией) - на деле сравнивались ДВА НЕЗАВИСИМЫХ
  случайных прогона, не один и тот же шум под разным трением. Честная
  переоценка: качественное наблюдение (агар - плавно бегущий пик, вода -
  резкие перескоки) МОГЛО быть артефактом сравнения разных случайных
  реализаций шума, а не разницы сред как таковой - открытый вопрос,
  требует переизмерения на исправленном коде.
- Любая single-run диагностика через `trace`, где сид указывался с расчётом
  на воспроизводимость между отдельными запусками процесса.

**Исправление**: `std::srand(time(nullptr))` удалён из конструктора
`WormSim` целиком - сидирование полностью на совести вызывающего кода, как
и предполагали все тесты изначально. Для живого `Demo_worm` разовое
`std::srand(time(nullptr))` добавлено в `main()`, до конструктора `WormApp`
(один раз за весь процесс, не при каждом создании `WormSim`).

**Подтверждено**: `ctest` (`Test_worm_locomotion`, `Test_worm_regression`)
- 100% PASS после фикса, числа не изменились (шипнутые дефолты дают то же
самое здоровье/скорость/частоту, что и раньше - фикс меняет ТОЛЬКО
воспроизводимость между процессами, не сам стек параметров). Отдельно
подтверждено напрямую: один и тот же `seed` в двух отдельных запусках
`Test_worm_v2_measurement.exe trace`, разделённых реальной 2-секундной
паузой, теперь даёт побитово идентичный результат - раньше (до фикса) не
совпадал бы.
