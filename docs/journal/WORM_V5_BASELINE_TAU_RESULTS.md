**Итог одной строкой**: Phase 1 (сиблинг-агент) доказала прямым инструментальным

один диагностический срез ОДНИМ уровнем раньше - сырое `net.state()`
мотонейронов (V, ДО `muscle_calcium_`/`muscle_output()`) - и нашла тот же
самый коллапс уже там: на 3 свежих сидах (агар, шипнутые дефолты, 2800 шагов)

роста со временем. **Вывод: коллапс уже присутствует в сырой V мотонейронов
(`net.state()`), т.е. рождается в собственной рекуррентной динамике сети НА
ОДИН ШАГ РАНЬШЕ, чем `muscle_calcium_`/`muscle_output()` успевает его хоть
как-то отфильтровать** - кальциевый фильтр (`muscleCalciumTau=0.1с`) вносит
лишь небольшую, примерно ПОСТОЯННУЮ (не растущую со временем) дополнительную
атенюацию, ожидаемую от обычного низкочастотного фильтра на фиксированной
частоте, а не механизм, который сам "стирает" сигнал по мере прогона.

## 1. Что было найдено в Isolate-фазе (Phase 1, сиблинг-агент)

Полный отчёт сиблинга приведён в брифинге этой задачи; кратко, для полноты
этого документа:

- Код (`WormSim.cpp`/`WormSim.h`) читается точно так, как описано в брифинге:
  `lastCurvatureDeviation()` -> `m_lastCurvature` хранит `deviation` ПОСЛЕ
  `kDeviationClamp=2.0`; `m_curvatureBaseline` - обычный `std::vector<float>`
  без инициализатора (ленивый `assign(...,0.0f)` при первом использовании);
  `kBaselineTau=4.0f` - локальный `constexpr` внутри `step()`, НЕ поле
  `Params` (до этой сессии).
- Добавлен (аддитивно, без изменения поведения) `debugRawCurvature()` /
  `m_lastRawCurvature` - снимок `curvature[i]` ДО вычитания
  `m_curvatureBaseline` (но ПОСЛЕ `bodyGain` и пространственного вычитания
  среднего по телу).
- Сборка + `ctest -R "Test_worm_locomotion|Test_worm_regression"`: **обе
  PASS**, числа `Test_worm_regression` побитово совпали с уже известной
  статистикой (`AGAR mean minSustainedBendAmplitude=0.0178 rad`, `WATER
  mean minSustainedBendAmplitude=0.0180 rad`) - подтверждено, что
  инструментирование не поменяло поведение.
- Измерение на 5 свежих сидах (агар, шипнутые дефолты, 2800 шагов): наивная
  статистика `max|curvature_i|` вводит в заблуждение - выходит на плато
  ~2.48-2.49 рад к шагу ~300 и остаётся там до конца прогона на КАЖДОМ сиде.
  Это не осцилляция, а крупный, устойчивый, **пространственно
  неоднородный** (НЕ "весь корпус в одну сторону" - именно за это отвечает
  уже отдельное вычитание среднего по телу строкой выше в `step()`) почти
  стационарный по времени паттерн на каждой позиции отдельно - то, ради чего
  `m_curvatureBaseline` и существует.
- Настоящая AC-компонента (peak-to-peak по 200-шаговым окнам на
  наиболее-осциллирующем узле) коллапсирует В ТЕЧЕНИЕ первых ~100-200 шагов
  в 6.5x-8.2x на 4/5 сидов (узел 2), и `dev[i]`/`curvature[i]` держат
  отношение ~0.85-1.08 равномерно по ВСЕМУ прогону (не растёт со временем) -
  что и стало прямым доказательством: **фильтр почти не трогает реальную
  осцилляцию (пропускает её на ~85-108%), коллапс уже находится в самом
  `curvature[i]`, ДО фильтра**.

**Вердикт Phase 1: REAL.** См. раздел 2 этой задачи ("do NOT attempt the
kBaselineTau lever") - соответственно, `kBaselineTau`/
`m_curvatureBaseline` в этой фазе не трогались НИ РАЗУ, ни как код, ни как
параметр.

## 2. Что сделано в этой фазе (Phase 2) - аддитивная диагностика ОДНИМ уровнем раньше

Цель: раз коллапс уже присутствует в `curvature[i]` (= `net.muscle_output(id)`
per-position, после `bodyGain`), проверить, есть ли он ЕЩЁ РАНЬШЕ - в сыром
`net.state(id)` мотонейронов, до `muscle_calcium_`/`muscle_output()`
(`connectome::Network::muscle_output`, `network.hpp`):

```cpp
float muscle_output(NeuronId id) const {
    return muscle_calcium_tau_ > 1e-6f ? muscle_calcium_[id] : state_[id];
}
```

При шипнутом `muscleCalciumTau=0.1с` (не 0) `muscle_output()` возвращает
`muscle_calcium_[id]` (Ca, релаксирует к V с постоянной времени 0.1с), а НЕ
`state_[id]` (V) напрямую - то есть `curvature[i]`/`debugRawCurvature()` уже
видит сигнал ПОСЛЕ одного каскада НЧ-фильтрации. Вопрос Phase 2: коллапс уже
есть в самом V, или его вносит именно этот Ca-фильтр (либо `muscleLeakScale`/
взаимодействие leak-ёмкость на `Output`-нейронах)?

### 2.1. Изменения (все - аддитивные, без изменения существующих вычислений)

- **`demo/worm/WormSim.h`**:
  - новый член `std::vector<float> m_lastRawMotorVoltage;` рядом с
    `m_lastRawCurvature` (тот же паттерн);
  - новый публичный accessor `debugRawMotorVoltage()`, зеркалящий
    `debugRawCurvature()`/`debugBodyAngles()`.
- **`demo/worm/WormSim.cpp`**: в `step()`, в том же цикле `for (int pos = 1;
  pos <= 24; ++pos)`, который уже считает `curvature[pos-1] = (d - v) *
  bodyGain` через `net.muscle_output(id)`, добавлен ПАРАЛЛЕЛЬНЫЙ расчёт того
  же `(d - v) * bodyGain`, но через `net.state(id)` (та же пара
  `m_dorsalByPos`/`m_ventralByPos`, тот же `bodyGain`) - результат копируется
  в `m_lastRawMotorVoltage` ПОСЛЕ цикла. Ничего из существующего кода не
  читает `rawMotorVoltage`/`m_lastRawMotorVoltage` - чисто диагностический
  снимок, ноль влияния на `curvature`/`deviation`/тело/сеть.
- **`tests/worm_v2_measurement/main.cpp`**: в `dumpPhase`-блоке `trace`-режима
  добавлена четвёртая печатаемая строка на шаг, `voltage <i>: <24 floats>`,
  через `sim.debugRawMotorVoltage()`, по тому же паттерну, что уже
  существующие `phase`/`angles`/`curvature` строки.

Никакой `Params`-параметр НЕ добавлен и НЕ изменён в этой фазе - по прямому
запрету задачи ("Do not implement or ship any parameter change in this
branch of the task - only characterize further").

## 3. Методология измерения (Phase 2)

Тот же принцип, что в Phase 1 (200-шаговый peak-to-peak на
"наиболее-осциллирующем" узле - см. `analyze_curvature.py` в

grep-проверенных против полного списка сидов, встречавшихся где-либо в
scratchpad-е этой сессии (сотни значений, диапазоны 13-800020 плюс
специфичные сиды из Phase 1: `42, 111, 999, 12345, 31337, 424242, 500001,
700001, 998877, 246813579, 730815, 84512, 913377, 208465, 651902` - ни один
не совпал):

- **617283, 823456, 194837**
- агар (`dragNormal=40`), **шипнутые дефолты без единого override**
  (`bodyGain=-1`, `mechanoGain=0`, `localMechanoGain=0`,
  `bodyBendStiffness=0`, `proprioceptiveOffset=-1`, `proprioceptiveGain=-1` -
  все "<=0 = не трогать дефолт" в `trace`-режиме `tests/worm_v2_measurement`),
  2800 шагов, `dumpPhase=1`.
- Команда: `Test_worm_v2_measurement.exe trace <seed> 2800 40 -1 0 0 1 0 -1 -1`.
- Заголовок каждого трейса подтверждает шипнутые значения:
  `muscleLeak=50.00 muscleCaTau=0.10 poseDecay=0.60 frameRateHz=2.00
  bendStiffness=0.00 propOffset=4.00 propGain=4.00` - совпадает с Phase 1.

Для каждого сида: выбирается "наиболее-осциллирующий" узел по
peak-to-peak `curvature[node]` в устоявшемся окне [1500,2800) (тот же метод,
что `best_oscillating_node()` в `analyze_curvature.py` Phase 1 - НЕ окно
[0,200), чтобы результат был сравним напрямую с уже опубликованными числами
Phase 1 по узлу); для этого узла считаются: (a) `curvature[node]` peak-to-peak
в окне [0,200) против среднего peak-to-peak по 200-шаговым чанкам в
[1500,2800); (b) то же самое для `voltage[node]` (тот же узел, для
прямого apples-to-apples сравнения); (c) полная по-чанковая раскладка обеих
серий на всём прогоне 0-2800, чтобы увидеть, растёт ли отношение voltage/
curvature со временем (= фильтр всё сильнее "съедает" сигнал) или остаётся
плоским (= фильтр просто масштабирует, коллапс уже был во входе).

Скрипт анализа: `analyze_voltage.py` (в том же scratchpad-е, что и Phase 1's
`analyze_curvature.py`). Трейс-логи: `voltage_traces/seed_*.log`.

## 5. Интерпретация

1. **Коллапс уже полностью присутствует в `net.state()`** (сырое V
   мотонейронов, до какого-либо фильтра муxскулатуры) - `voltage`
   коллапсирует на 6.25x-10.54x между [0,200) и устоявшимся плато, что того
   же порядка величины, что и коллапс `curvature` (7.41x-13.93x) на тех же
   сидах/узлах. Это не "почти нет коллапса в V, весь коллапс - от Ca-фильтра"
   - оба сигнала теряют примерно один порядок величины амплитуды в одном и
   том же временном окне.
2. **`muscle_calcium_`/`muscleCalciumTau=0.1с` вносит лишь небольшую,
   стабильную во времени дополнительную атенюацию** (~1.0-1.4x, `curvature`
   систематически чуть МЕНЬШЕ, чем `voltage` - фильтр не усиливает, слегка
   гасит, как и положено НЧ-фильтру на ненулевой частоте) - и эта атенюация
   **не растёт** от начала прогона к его концу. Это ожидаемое поведение
   line­ar time-invariant НЧ-фильтра на сигнале с примерно постоянной
   частотой (что и подтверждает Phase 1 отдельно для `m_curvatureBaseline`):
   фиксированный коэффициент пропускания, не эволюционирующий во времени
   механизм подавления.
3. **Значит: распад амплитуды рождается ДО `muscle_output()`/
   `muscle_calcium_` - то есть в собственной рекуррентной динамике сети,
   формирующей `net.state()` `Output`-нейронов** (chem/gap-токи от
   `ProcessingOutput`/`Processing` слоёв + `leak`/`muscleLeakScale` на самих
   `Output`-нейронах - см. класс-комментарий `Network` в `network.hpp` за
   архитектурой этих слоёв). Это НЕ artefact измерения (тот же вывод, что и
   Phase 1 для `curvature` относительно `dev`) и НЕ специфично для мышечной
   стадии (`muscleCalciumTau`/`muscleLeakScale`) - оба уже были испробованы и
   провалились как отдельные рычаги темпа (см. `WORM.md` раздел 6 и
   `Params::muscleCalciumTau`/`muscleLeakScale` комментарии в `WormSim.h`), и
   эта диагностика подтверждает, что вопрос "почему выход мышцы мал" даже НЕ
   про них - амплитуда уже мала в самой сети, а не становится малой ИЗ-ЗА
   мышечной фильтрации поверх якобы большого сетевого сигнала.
4. Открытый нюанс, честно НЕ разрешённый этой диагностикой: коллапс
   ~[0,200) -> плато можно прочитать двумя способами - (a) сеть стартует из
   V=0 для всех нейронов и первые ~100-200 шагов - это переходный процесс
   выхода на СВОЙ настоящий предельный цикл (в этом случае большая амплитуда
   [0,200) - не более "настоящая", чем cold-start baseline - а маленькая
   settled-амплитуда и есть подлинный установившийся режим сети); или (b)
   сеть ДЕЙСТВИТЕЛЬНО имеет предельный цикл большей амплитуды, но что-то
   (насыщение сигмоиды активации, проприоцептивная обратная связь, что-то
   ещё) постепенно "детюнит" её к меньшей амплитуде по ходу прогона. Эта
   диагностика (voltage vs curvature на одном и том же узле) отвечает ТОЛЬКО
   на вопрос "на каком слое конвейера коллапс уже присутствует" (ответ: на
   слое `net.state()`, не позже) - она НЕ отвечает на вопрос "почему сеть
   выбирает такую маленькую установившуюся амплитуду". Это следующий,
   отдельный вопрос (см. раздел 6).

мышечной стадии**:

1. **Ещё один уровень выше**: параллельный accessor для `net.state()`
   отдельно по `ProcessingOutput`/`Processing`-слоям (не только
   `Output`-мотонейронов, уже сделано этой фазой) - тем же per-position или
   per-нейрон способом, чтобы увидеть, коллапсирует ли AC-амплитуда
   premotor/командных интернейронов ТЕМ ЖЕ темпом (= распад ещё выше,
   в командном слое или во входных сенсорных/проприоцептивных каналах) или
   их собственная амплитуда остаётся большой, а коллапс возникает именно НА
   `Output`-нейронах (= что-то специфичное для `leak`/`muscleLeakScale`
   именно этого типа нейронов, `Network::set_muscle_leak`, честно
   упомянутое как "не откалибровано" в его собственном комментарии).
2. **Разделить транзиент от установившегося режима явно**: повторить тот же
   `voltage`/`curvature` замер, НО стартуя сеть не из V=0, а из уже
   установившегося (например, снятого на шаге 2000 предыдущего прогона)
   состояния - если коллапс всё равно происходит (т.е. большая амплитуда
   возвращается при большом стартовом V, а потом снова падает) - это говорит
   в пользу пункта (b) раздела 5 (детюнинг, а не просто cold-start
   переходный процесс); если нет - это подтверждает (a) (первые ~200 шагов
   были переходным процессом самой сети, не более "реальными", чем
   cold-start `m_curvatureBaseline`, который Phase 1 уже оправдала).

Ни один из этих двух шагов не реализован в этой сессии - оба помечены как
открытые вопросы для следующей, по прямому требованию задачи ("narrows the
next investigation even if you don't fix anything this round").
